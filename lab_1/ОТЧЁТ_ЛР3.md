## 2. Цель этапа А

Превратить синхронные анализаторы в управляемый исполнитель заданий:
ограничить конкурентность и очередь, добавить тайм-ауты и отмену, сохранить
результаты и адаптировать синхронный анализ ЛР1 к выбранной модели исполнения.
Постоянное хранение и пользовательский интерфейс относятся к следующему этапу.

## 3. Выполненные требования

### Модель задачи и статусы

-   [x] `AnalysisJob` содержит `job_id`, `submission_id`, `submission_hash`,
    `analyzer_id`, `config_hash`, `status`, `attempt_no`, тайм-аут и timestamps.
-   [x] Используется общий контракт статусов: `queued`, `running`,
    `succeeded`, `failed`, `timed_out`, `cancelled`, `rejected`.
-   [x] Постановка задачи (`build_analysis_job`, `submit`) отделена от
    выполнения worker-циклами.
-   [x] Результат успешной задачи сохраняется в памяти до этапа Б.

### Очередь и конкурентность

-   [x] `concurrency_limit` ограничивает число одновременно работающих
    анализаторов.
-   [x] `queue_limit` ограничивает очередь; переполнение даёт явный отказ
    `queue_full`.
-   [x] Исходная сдача сохраняется до проверки очереди и не теряется при
    отказе.
-   [x] `queue_limit=0` означает «только при свободной мощности».

### Тайм-аут и отмена

-   [x] У каждой задачи есть `timeout_seconds`.
-   [x] Тайм-аут даёт отдельный статус `timed_out` и код `timeout`.
-   [x] Отмена поддерживается до старта и во время выполнения.
-   [x] `CancelledError` не превращается в обычную ошибку анализатора.
-   [x] Для отменённой задачи результат не сохраняется.

### Модель исполнения

-   [x] Синхронный анализ ЛР1 адаптирован через `SyncAnalyzerAdapter`.
-   [x] CPU-анализ выполняется в отдельном пуле и не блокирует event loop.
-   [x] Сравнены последовательный запуск, потоки и процессы; выбор обоснован
    измерениями.

### AI/MLOps

-   [x] `GuardedModelAdapter` ограничивает конкурентные обращения к модели.
-   [x] `BatchConfig` фиксирует размер пакета, `concurrency_limit` и тайм-аут.
-   [x] Тайм-аут, недоступность и невалидный ответ имеют разные коды.
-   [x] Замена `StubModelAdapter` на другой адаптер не меняет управление
    задачей.
-   [x] Автоматические повторы не реализованы: они запланированы на ЛР4.

## 4. Архитектура

| Слой | Компонент | Ответственность |
|---|---|---|
| Модель | `AnalysisJob`, `JobStatus`, `JobErrorCode` | Контракт задачи и статусов |
| Хранение этапа А | `JobStore`, `InMemoryRepository` | Задачи и сдачи в памяти |
| Исполнитель | `AnalysisExecutor`, `ExecutorConfig` | Очередь, worker'ы, тайм-аут, отмена |
| Адаптеры | `SyncAnalyzerAdapter`, `SlowAdapter`, `GuardedModelAdapter` | Граница между задачей и конкретным анализатором/моделью |
| Наблюдаемость | `SubmitResult`, `job.to_dict()`, `stats()` | Явный отказ и состояние очереди |

Исполнитель не знает, синхронный перед ним анализатор или модельный адаптер:
он вызывает `analyze` и обрабатывает общий набор кодов ошибок.

## 7. Проверки

```bash
pytest tests/ -q
```

Результат: **124 passed, 1 warning**. Из них 47 тестов относится к ЛР3-A:
модели задач, исполнитель, модельный адаптер и обязательные проверки.
Предупреждение — устаревший `noload` внутри SQLAlchemy/MLflow, к ЛР3 не
относится.

Ключевые проверки:

-   лимит конкурентности и переполнение очереди;
-   отказ без потери исходной сдачи;
-   тайм-аут как отдельный статус;
-   отмена до старта и во время выполнения;
-   неблокирующий event loop на CPU-анализе;
-   разные коды для timeout/unavailable/invalid response;
-   фиксированный batch size и лимит конкурентных вызовов модели;
-   замена stub на другой адаптер без изменения управления задачей.

### Политика ошибок

Выбрана **collect-errors**: каждая задача изолирована, ошибка или тайм-аут
одной задачи не останавливает остальные. Результаты успешных задач остаются в
`JobStore` и доступны через `get_result` / `results`. Fail-fast не
используется, потому что при пакетной проверке работ потеря остальных
результатов из-за одной ошибки недопустима.

## 8. Ограничения этапа А

1. Хранение задач и результатов — в памяти; после перезапуска данные теряются,
   история задач растёт линейно. Очередь ограничена `queue_limit`.
2. Пользовательский интерфейс не реализован.
3. Отмена синхронной функции в потоке кооперативная: поток не убивается
   принудительно. `shutdown` дожидается уже запущенного вызова пула, поэтому
   после остановки неуправляемых задач не остаётся. Для жёсткой отмены нужен
   процессный пул.
4. Нет автоматических повторов временных ошибок — это ЛР4.
5. Нет внешнего брокера и распределённой очереди.
6. Модель — детерминированная заглушка; реальный API не вызывается.
7. `ProcessPoolExecutor` на Windows требует `if __name__ == "__main__"` и
   сериализуемых адаптеров, поэтому не является режимом по умолчанию.
8. Один экземпляр исполнителя привязан к одному event loop.
