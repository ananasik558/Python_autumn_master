идемпотентность и FastAPI-интерфейс.

## 2. Цель работы

Этап А — превратить синхронные анализаторы в управляемый исполнитель:
ограничить конкурентность и очередь, добавить тайм-ауты и отмену, сохранить
результаты и не блокировать event loop.

Этап Б — сохранить `Submission`, `AnalysisJob` и `AnalysisReport` в SQLite,
добавить идемпотентный запуск анализа и HTTP-интерфейс с контролем доступа.

## 3. Этап А: ограниченный исполнитель

### 3.1. Выполненные требования

-   [x] `AnalysisJob` содержит `job_id`, `submission_id`, `submission_hash`,
    `analyzer_id`, `config_hash`, `status`, `attempt_no`, тайм-аут и timestamps.
-   [x] Контракт статусов: `queued`, `running`, `succeeded`, `failed`,
    `timed_out`, `cancelled`, `rejected`.
-   [x] Постановка задачи (`build_analysis_job`, `submit`) отделена от
    выполнения worker-циклами.
-   [x] `concurrency_limit` ограничивает одновременно работающие задачи.
-   [x] `queue_limit` ограничивает очередь; переполнение даёт `queue_full`.
-   [x] Исходная сдача сохраняется до проверки очереди и не теряется при
    отказе.
-   [x] У каждой задачи есть `timeout_seconds`; тайм-аут даёт `timed_out` /
    `timeout`.
-   [x] Отмена поддерживается до старта и во время выполнения.
-   [x] `CancelledError` не превращается в обычную ошибку анализатора.
-   [x] Для отменённой задачи результат не сохраняется.
-   [x] Синхронный анализ ЛР1 адаптирован через `SyncAnalyzerAdapter`.
-   [x] CPU-анализ выполняется в отдельном пуле и не блокирует event loop.
-   [x] `GuardedModelAdapter` ограничивает конкурентные обращения к модели,
    фиксирует `batch_size`, различает timeout/unavailable/invalid response.
-   [x] Замена `StubModelAdapter` на другой адаптер не меняет управление
    задачей.
-   [x] Автоматические повторы не реализованы: они запланированы на ЛР4.

### 3.2. Архитектура

| Слой | Компонент | Ответственность |
|---|---|---|
| Модель | `AnalysisJob`, `JobStatus`, `JobErrorCode` | Контракт задачи и статусов |
| Хранение А | `JobStore`, `InMemoryRepository` | Задачи и сдачи в памяти |
| Исполнитель | `AnalysisExecutor`, `ExecutorConfig` | Очередь, worker'ы, тайм-аут, отмена |
| Адаптеры | `SyncAnalyzerAdapter`, `SlowAdapter`, `GuardedModelAdapter` | Граница между задачей и анализатором/моделью |
| Наблюдаемость | `SubmitResult`, `job.to_dict()`, `stats()` | Явный отказ и состояние очереди |

Очередь разделена на `_starting` (зарезервированные немедленные старты) и
`_pending` (ожидание). Поэтому `pending_count` не превышает `queue_limit`.
Исполнитель не знает, синхронный перед ним анализатор или модель: он вызывает
`analyze` и обрабатывает общий набор кодов ошибок.

### 3.3. Тайм-аут, отмена и ошибки

-   `shutdown` дожидается уже запущенных вызовов пула, поэтому после остановки
    нет задач, которыми исполнитель больше не управляет.
-   Выбрана политика **collect-errors**: ошибка, тайм-аут или отмена одной
    задачи не останавливают остальные; результаты успешных задач сохраняются.
-   Для детерминированных проверок используются `asyncio.Event`,
    `GateAdapter`, `threading.Event` и `SlowSyncAnalyzer`, а не случайные
    задержки.

## 4. Этап Б: хранение и интерфейс

### 4.1. Выполненные требования

-   [x] `Submission` хранится в SQLite и не изменяется при повторной отправке
    с тем же `submission_id`.
-   [x] `AnalysisJob` и `AnalysisReport` хранятся в SQLite.
-   [x] `succeeded` и отчёт пишутся в одной транзакции.
-   [x] `succeeded` без отчёта отклоняется при записи и не выдаётся как успех.
-   [x] После перезапуска история доступна; `queued`/`running` помечаются
    `failed` / `interrupted`.
-   [x] Несогласованная запись `succeeded` без отчёта помечается `failed` /
    `inconsistent_state`.
-   [x] `attempt_no` и история попыток сохраняются.
-   [x] `idempotency_key` хранится в БД.
-   [x] Тот же ключ с теми же `submission_hash`, `analyzer_id`, `config_hash`
    возвращает тот же job.
-   [x] Тот же ключ с другим payload даёт `409 idempotency_conflict`.
-   [x] Повтор после `failed` с тем же ключом возвращает тот же failed job.
-   [x] Новый ключ после failed создаёт новую попытку с `attempt_no + 1`.
-   [x] Job и idempotency key создаются одной транзакцией; при конфликте ключа
    job не остаётся «осиротевшей».
-   [x] FastAPI + SQLite; PostgreSQL не требуется.
-   [x] Контроль доступа по `X-API-Key` или `Authorization: Bearer`.
-   [x] Роли: student, teacher, admin; студент видит только свои работы,
    преподаватель — только работы своих заданий.
-   [x] Ответы API не содержат ключ доступа и секрет провайдера.
-   [x] Baseline и model-adapter работают через один контракт `AnalysisAdapter`.
-   [x] В отчёте хранятся `model_version`, `index_version`, `prompt_version`,
    `config_hash`, `mlflow_run_id`.
-   [x] Режим `unavailable` позволяет работать без внешней модели.

### 4.2. Схема и атомарность

Таблицы: `submissions`, `jobs`, `analysis_reports`, `idempotency_keys`.

`SqliteJobStore.save` обновляет job и пишет report в одной транзакции. При
`status=succeeded` и отсутствии результата выбрасывается `PersistenceError`,
поэтому «готовый статус без результата» не сохраняется.

`SqliteStore.initialize()` при старте вызывает `recover_unfinished()`:

-   `queued`/`running` → `failed`, `error_code=interrupted`;
-   `succeeded` без report → `failed`, `error_code=inconsistent_state`.

Оригинальная сдача хранится отдельно и не перезаписывается. Для teacher-доступа
у сдачи сохраняется `assignment_id`.

### 4.3. Идемпотентность

-   Тот же ключ и тот же payload → тот же `job_id` (идемпотентный повтор).
-   Тот же ключ и другой payload → `409`.
-   Новый ключ после failed → новая попытка, `attempt_no` увеличивается,
    история остаётся.
-   Ключ можно передать в теле или заголовком `Idempotency-Key`.
-   Повтор после перезапуска читает сохранённый ключ из SQLite.

### 4.4. API и доступ

Запуск:

```bash
uvicorn submission_system.api.app:create_app --factory --reload
```

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/health` | Доступность и счётчики recovery; без ключа |
| POST | `/submissions` | Создать/получить неизменяемую сдачу |
| GET | `/submissions` | Список сдач с учётом роли |
| GET | `/submissions/{id}` | Оригинальная сдача |
| POST | `/analysis-jobs` | Запуск анализа по idempotency_key |
| GET | `/analysis-jobs` | История задач с учётом роли |
| GET | `/analysis-jobs/{id}` | Статус и результат |
| GET | `/analysis-jobs/{id}/report` | Отчёт |
| POST | `/analysis-jobs/{id}/cancel` | Отмена |
| GET | `/analyzers` | Baseline и model-adapter |

API-маршруты также доступны с префиксом `/api/v1`.

Ключи и роли:

-   `ANALYZER_API_KEY` — admin, полный доступ;
-   `ANALYZER_STUDENT_KEYS` — JSON `{"student-key":"student-id"}`;
-   `ANALYZER_TEACHER_KEYS` — JSON `{"teacher-key":["hw_1","hw_2"]}`.

Студент может читать и запускать только свои работы. Преподаватель видит
отчёты только по своим `assignment_id`; запуск и отмена ему запрещены. Admin
видит всё.

## 6. Измерения

Измерение на одном наборе: 20 задач, 3 worker'а, `queue_limit=20`,
200 000 итераций CPU-нагрузки на задачу, 3 повтора. Нагрузка — синтетический
`CpuBoundAnalyzer`, качество анализа не измеряется.

| Режим | Wall time, median | Throughput, median | Ошибки |
|---|---:|---:|---:|
| последовательный | 0.414 s | 48.27 jobs/s | 0 |
| потоки (выбранный) | 0.404 s | 49.45 jobs/s | 0 |
| процессы | 0.506 s | 39.54 jobs/s | 0 |

Выбран пул потоков: на учебном CPU-наборе он немного быстрее
последовательного режима, не требует сериализации объектов между процессами
и не платит за spawn на Windows. Ускорение не является обязательным: при
такой нагрузке выигрыш небольшой (≈2.4%), но отсутствие большого выигрыша
объяснимо GIL и накладными расходами. Пул процессов оставлен опцией для
будущих тяжёлых CPU-адаптеров.

Ошибки в нагрузочном прогоне равны 0, потому что сбои не инжектировались;
обработка timeout/unavailable/invalid response проверена отдельными тестами.
Артефакт: `artifacts/lab3/executor_benchmark.json`.

## 8. Ограничения

1. SQLite рассчитан на один сервисный процесс; `recover_unfinished`
   предполагает отсутствие других активных исполнителей на той же БД.
2. Идемпотентность защищена `asyncio.Lock` в одном процессе; для нескольких
   реплик нужен внешний координатор.
3. Отмена синхронной функции в потоке кооперативная: поток не убивается
   принудительно; `shutdown` дожидается уже запущенного вызова пула.
4. Нет автоматических повторов временных ошибок — это ЛР4.
5. Внешняя модель не вызывается: stub или режим `unavailable`.
6. MLflow-run хранится ссылкой; сервер MLflow не поднимается.
7. Архивация и ротация истории не реализованы.
8. Интерфейс — JSON API и Swagger, отдельного frontend нет.
9. `ProcessPoolExecutor` на Windows требует `if __name__ == "__main__"` и
   сериализуемых адаптеров, поэтому не является режимом по умолчанию.
10. Один экземпляр исполнителя привязан к одному event loop.

## 9. Использование ИИ

ИИ использовался для черновиков документации, обсуждения контракта статусов,
схемы SQLite, идемпотентности и маршрутов API. Код, миграция схемы,
бенчмарки, тесты и выводы проверены запуском локально; реальные персональные
данные и внешние модельные API не использовались. Подробнее — `AI_USAGE.md`.
